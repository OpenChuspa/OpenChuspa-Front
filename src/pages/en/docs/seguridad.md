# Security

OpenChuspa stores other people's data, so every default is the secure one. What is not protected yet is documented below, in Known limits.

## What it does by default

- **It does not start open:** without credentials, with a secret shorter than 32 characters or in anonymous mode outside loopback, it refuses to start.
- **It verifies every signature:** SigV4 by header, with a 15-minute window and constant-time comparisons. It also verifies the signature of every chunk of `aws-chunked` bodies and every declared checksum; if anything does not match, the object is not stored.
- **It stops brute force:** 20 failed authentications in one minute from an IP block it for 5 minutes, with `503 SlowDown`.
- **Keys are never paths:** content is stored under random names generated by the server, so a key like `../../etc/passwd` cannot write outside the data folder.
- **Never a fake success:** what is not implemented returns `501`, and a header asking for something the engine does not do (public ACL, encryption, object lock) is rejected instead of ignored.
- **Logs without secrets:** headers and the query string are never logged. CI checks it on every change.
- **Minimal image:** distroless, no shell, running as an unprivileged user, compatible with a read-only filesystem and without capabilities.

## TLS

Outside loopback, the engine needs TLS: its own or that of a proxy in front. Without either, it warns in the log at startup.

```yaml
    environment:
      CHUSPA_TLS_CERT_FILE: /run/secrets/tls_cert
      CHUSPA_TLS_KEY_FILE: /run/secrets/tls_key
```

The minimum is TLS 1.2. The certificate is reloaded when it changes on disk, so a renewal (Let's Encrypt, cert-manager) does not need a restart. If the new file does not load, the previous one keeps being served.

Behind a proxy, brute-force blocking sees the proxy's IP: an attack blocks everyone for 5 minutes. That is preferred over allowing unlimited key guessing. If the proxy already limits attempts, adjust it with `CHUSPA_AUTH_MAX_FAILURES`.

## Rotate the secret without downtime

1. Generate the new one: `openssl rand -hex 24`.
2. Put the new one in `CHUSPA_ROOT_PASSWORD` and the current one in `CHUSPA_ROOT_PASSWORD_PREVIOUS`. Restart the engine: it accepts both.
3. Change the secret in every client.
4. Remove `CHUSPA_ROOT_PASSWORD_PREVIOUS` and restart.

While a previous secret is configured, the log reminds you at startup.

## Supply chain

- Every release publishes the image signed with keyless cosign, with SBOM and provenance, and the binaries with their signed SHA-256 sums. To verify them, see [Installation](/en/docs/instalacion/#verify-the-image).
- Dependencies go through `govulncheck` and a license review on every change, and CI actions are pinned by SHA.
- Every night, fuzzing runs against the parsers of untrusted input: signatures, `aws-chunked` bodies and ranges.

## Known limits

- A single credential with full access. Users and policies arrive in phase 2.
- No encryption at rest: protect the disk (for example, with volume encryption). Arrives in phase 3.
- Whoever has write access to the data volume can alter it. Periodic verification detects content changes but does not prevent them.
- It has not been through an external security audit.

## Report a vulnerability

Do not open a public issue. Use GitHub private reporting: **Security** tab of the [OpenChuspa-core](https://github.com/OpenChuspa/OpenChuspa-core) repository, **Report a vulnerability** button. Response commitments: acknowledgement within 72 hours, assessment within 7 days, and a fix with coordinated disclosure within 90 days at most.
